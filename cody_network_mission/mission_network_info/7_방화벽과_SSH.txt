1. 방화벽
    1-1.미리 설정된 보안 규칙에 따라 네트워크 트래픽을 허용하거나 차단하는 시스템입니다.
    1-2. AWS EC2에 웹 서버
        서버 IP 주소: 203.0.113.10 (예시 주소)
        실행 중인 서비스
        - 웹 서버: TCP 80
        - HTTPS 서버: TCP 443
        - SSH 서버: TCP 22
        => 웹 서버는 누구나 이용 가능, 서버에 관리자로 접속은 자신만 허용하고 싶을 떄
            방화벽에 규칙을 설정합니다.
    
    1-3. 방화벽 정보 확인
        => 출발지 IP, 목적지 IP, 프로토콜, 출발지 포트, 목적지 포트, 연결 상태.. 등 정보를 이용해 
            트래픽을 제어할 수 있습니다.


2. 인바운드, 아웃바운드
    2-1. 특정 컴퓨터나 네트워크를 기준으로 트래픽이 들어오는지, 나가는지 구분하는 개념입니다.
    2-2. 사용자가 EC2 서버에 요청
        => 서버 입장에서 외부에서 연결 요청이 들어오므로 인바운드 트래픽입니다.
    
    2-4. 내 서버가 외부 API를 호출
        => 서버 입장에서 외부로 연결을 보내므로 아운바운드 트래픽입니다.
        => 또는 서버의 응답도 아운바운드 트래픽입니다.

        => EC2 네트워크 인터페이스에 적용되는 가상 방화벽
    
    3-2. 인바운드 규칙 예시
    유형	 포트	    출발지	               의미
    HTTP	TCP 80	    0.0.0.0/0	        모든 IPv4 주소에서 HTTP 허용
    HTTPS	TCP 443	    0.0.0.0/0	        모든 IPv4 주소에서 HTTPS 허용
    SSH	    TCP 22	    198.51.100.25/32	특정 관리자 IPv4 주소만 허용
    
    3-3. 아웃바운드 규칙 예시
    프로토콜	 목적지	               의미
    TCP 443 	0.0.0.0/0	        외부 HTTPS 서비스에 연결 가능
    TCP 3306	DB 서버 보안 그룹	  허용된 DB 서버에 MySQL 연결 가능

    3-4. AWS 보안 그룹의 특징은 상태 저장입니다.
        => 서버의 인바운드 TCP 443 연결 요청을 허용했다면,
             그 연결에 대한 정상적인 응답 트래픽은 별도의 아웃바운드 허용 규칙 없이도 전달될 수 있습니다.
        => 보안 그룹은 허용 규칙을 정의하는 방식이며, 명시적인 거부 규칙을 추가하는 방식은 아닙니다.

4. SSH
    4-1. 네트워크를 통해 다른 컴퓨터에 안전하게 원격 접속하기 위한 프로토콜입니다.
    4-2. 예시
        => 컴퓨터는 집, AWS 서버 데이터 센터
        => EC2 서버에 프로그램 설치 및 로그 확인하려면 서버에 명령어를 실행해야 합니다.
        => 이 떄 SSH를 사용합니다.
        => ssh ubuntu@203.0.113.10 -> 서버에 ubuntu 사용자 계정으로 SSH 접속을 시도한다는 뜻입니다.
        => 서버는 접속하려는 사람이 실제로 허가된 사용자인지 어떻게 확인할까?


5. 공개키 인증
    5-1. 공개키 암호 방식
        => 두 개의 키를 사용합니다.
        => 공개키(Public Key): 다른 사람에게 공개해도 되는 키
        => 개인키(Private Key): 소유자만 안전하게 보관해야 하는 키
        => SSH의 공개키 인증에서는 일반적으로 개인키로 자신의 신원을 증명하고,
             서버는 공개키로 그 증명을 검증합니다.
    
    5-2. 공개키는 서버, 개인키는 내 컴퓨터에 저장합니다.

    5-3. SSH 공개키 인증 과정
        1. 사용자의 컴퓨터에 개인키가 있고, 서버에는 해당 공개키가 등록되어 있습니다.
        2. 사용자가 서버에 SSH 접속을 요청합니다.
        3. SSH 클라이언트는 개인키를 사용하여 인증에 필요한 데이터에 디지털 서명을 생성합니다.
        4. 서버는 등록된 공개키를 사용하여 서명이 올바른지 검증합니다.
        5. 검증에 성공하고 다른 접속 조건도 만족하면 로그인을 허용합니다.
        => 가장 중요한 점은 개인키는 서버로 보내지 않습니다.
        => 서버는 개인키 자체를 받지 않고도, 사용자가 해당 개인키를 가지고 있다는 사실을 검증할 수 있습니다.
