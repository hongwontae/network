1. AWS VPC
    1-1. AWS 클라우드 내부에 사용자가 구성하는 논리적으로 격리된 가상 네트워크입니다.
    1-2. VPC CIDR: 10.0.0.0/16
        => PC에 할당된 IPv4 주소 범위는 10.0.0.0 ~ 10.0.255.255
        => 총 65,536개의 IPv4 주소가 포함
        => 이 주소 범위 안에서 서브넷을 나누고 EC2에 사설 IP를 할당할 수 있습니다.
        => 다른 VPC와는 기본적으로 네트워크가 분리됩니다.


2. Subnet
    2-1. VPC의 IP 주소 범위를 더 작은 네트워크로 나눈 것입니다.
    2-2. 예시
        => VPC 전체의 주소 범위가 10.0.0.0/16
        구분	             CIDR	         주소 범위
        Public Subnet	    10.0.1.0/24	    10.0.1.0 ~ 10.0.1.255
        Private Subnet	    10.0.2.0/24	    10.0.2.0 ~ 10.0.2.255
        => 각 서브넷은 256개의 IPv4 주소를 포함하지만, 
            AWS는 서브넷마다 5개를 예약하므로 일반적으로 251개를 사용할 수 있습니다.
    
    2-3. 서브넷으로 나누는 이유
        => 서버마다 필요한 네트워크 접근 수준이 다르기 때문입니다.
        => 웹 서버는 인터넷에서 사용자의 요청을 받아야 하지만, 
            데이터베이스 서버는 외부에서 직접 접근하지 못하게 하고 싶을 수 있습니다.


3. Route Table
    3-1. 네트워크 패킷을 어느 방향으로 전달할지 결정하는 규칙들의 집합입니다.
    3-2. AWS VPC에는 가상 라우터가 존재하고, Route Table을 통해 패킷을 어디로 보낼지 결정합니다.

    3-3. 192.128.1.0/24
        => 컴퓨터 A는 192.168.1.10 / 컴퓨터 B는 192.168.1.20 / 컴퓨터 C는 192.168.2.10
        => 컴퓨터 A와 B는 같은 네트워크에 속합니다. 데이터를 직접 보낼 수 있습니다.
        => 컴퓨터 A와 B에서 C로 보내려면 라우터에게 패킷을 보내고 라우터가 네트워크 패킷을 전달합니다.
        => 라우터가 여러 네트워크에 연결되어 있을 떄 목적지 IP를 보고 패킷을 어느 네트워크에 전달해야하는지 알아야 합니다.
        => 이 기준이 Route Table입니다.

        Destination	    Target
        192.168.1.0/24	네트워크 A
        192.168.2.0/24	네트워크 B
        0.0.0.0/0	    인터넷으로 나가는 경로
        => Destination: 패킷의 목적지 IP가 어떤 주소 범위에 속하는가?
        => Target: 그 주소 범위에 해당하는 패킷을 어느 방향으로 전달할 것인가?

    3-4. AWS VPC에서 10.0.0.0/16을 설정을 가정합니다.
        => 주소 범위는 10.0.0.0 ~ 10.0.255.255
        => Subnet A | 10.0.1.0/24 | 웹 서버 10.0.1.10
        => Subnet B | 10.0.2.0/24 | DB 서버 10.0.2.10
        => Destination | Target
           10.0.0.0/16 | local
           0.0.0.0/0   | Internet Gateway

        => 웹 서버가 DB 서버로 패킷을 보내려고 합니다.
        => 출발지는 10.0.1.10이고 목적지는 10.0.2.10입니다.
        => 목적지 10.0.2.10은 10.0.0.0/16 범위에 속합니다.
        => 그러면 local target이 local인 규칙이 선택됩니다.
        => local은 패킷을 VPC 내부에서 전달한다는 뜻입니다.
        => 두 서버가 서로 다른 Subnet에 속해 있어도 같은 VPC 주소 범위 안에 있어 VPC 내부 라우팅으로 통신 가능

        => 웹 서버가 구글의 DNS 서버 8.8.8.8로 패킷으로 보낸다고 가정합니다.
        => 0.0.0.0/0은 모든 IPv4 주소를 포함하는 CIDR입니다.
        => 8.8.8.8은 VPC 내부 주소 범위에 속하지 않아. 따라서 두 번째 규칙이 적용되어 Internet Gateway로 전달됩니다.

        => 라우팅 테이블은 여러 규칙이 일치할 경우 일반적으로 가장 구체적인 경로(Longest Prefix Match)를 선택합니다.
    
    3-5. IP 주소는 데이터가 도착해야 할 목적지를 알려줄 뿐, 그 목적지까지 어떤 경로로 가야 하는지 알려주지 않습니다.
        => 목적지를 아는 것과 목적지까지 가는 길을 아는 것은 별개의 문제입니다.
        => 컴퓨터 A: 192.168.1.10, 목적지 서버: 8.8.8.8, 기본 게이트웨이: 192.168.1.1
        => 컴퓨터 A가 데이터를 보내려면 목적지가 로컬 네트워크에 속하는지 확인합니다.
        => 다르다면 목적지 IP가 8.8.8.8인 패킷을 기본 게이트웨이인 192.168.1.1에 전달합니다.
        => IP 패킷의 목적지는 여전히 8.8.8.8이고, 로컬 링크에서 그 패킷을 전달받을 다음 장치가 라우터
        => 라우터도 자신의 라우팅 테이블을 확인해서 다음 경로를 선택합니다.
    
    3-6. 결론
        => 웹 서버가 10.0.2.10에 패킷을 보낸다면
            WS는 목적지 IP가 VPC 내부에 있다는 사실을 확인하고 local 경로를 선택합니다.
        => 8.8.8.8에 보내려면 VPC 외부로 나가야 하니까 Internet Gateway 경로를 선택합니다.
        => 결론적으로 IP 주소는 '어디로 가야 하는가'를 알려주고,
             라우팅 테이블은 '그곳으로 가려면 다음에 어디로 보내야 하는가'를 알려주는 역할을 합니다.
    
    3-7. IP 주소 중복
        => 서로 다른 사설 네트워크에 있는 컴퓨터들은 같은 ip를 사용해도, 인터넷에서 각 공유기의 공인 IP로 구별합니다.
        => 공유기는 NAT 변환 테이블을 관리해서, 어떤 내부 컴퓨터가 요청을 보냈는지 기억합니다.

        => 예시
        => 두 개의 컴퓨터가 존재하고 두 개의 컴퓨터는 같은 IP 주소를 사용하고 각자의 공유기가 존재
        => 두 컴퓨터의 사설 IP는 192.168.1.10으로 동일
        => 두 컴퓨터가 모두 외부 서버 8.8.8.8의 UDP 53번 포트로 DNS 요청
        => 외부 서버가 이 사설 IP만 본다면 어느 집의 컴퓨터인지 알 수 없기에 공유기가 NAT를 수행합니다.
        => 컴퓨터 A의 패킷이 공유기 A를 통과할 때, 공유기는 출발지 IP를 자신의 공인 IP로 바꿉니다.
        => 공유기는 203.0.113.10:40001	192.168.1.10:50000를 기록합니다.
        => 컴퓨터 B의 패킷이 공유가 B를 통과할 떄도 같은 현상이 일어납니다.
        => 외부 서버에는 출발지 IP가 서로 다른 두 요청이 도착하게 되는 것입니다.
        
        => 완벽히 분리된 네트워크 A,B를 사용할 떄는 NAT 이용없이도 통신이 가능합니다.
        => 그러나, 하나의 서버에 두 A,B가 요청을 보내면 문제가 발생합니다.


4. Internet Gateway
    4-1. VPC와 인터넷 사이의 통신을 가능하게 만드는 AWS 네트워크 구성 요소입니다.
    4-2. 집의 공유기가 인터넷 출입구 역할을 하는 것과 비슷합니다.


5. Security Group
    5-1. EC2와 같은 AWS 리소스에 적용하는 가상 방화벽입니다.
