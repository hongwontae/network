1. EC2에 접근하기 위한 외부 ip는 공인 ip입니다.
    => http://공인ip:port
    => http://43.202.47.71/?utm_source=chatgpt.com
    => 포트 번호를 생략했더라도 브라우저가 기본 포트를 자동으로 사용합니다.
    => http -> 80 == http://43.202.47.71:80/


2. AWS가 자동 할당한 공인 IPv4는 고정 IP가 아닙니다.
    => EC2를 중지 -> 시작 -> 바뀝니다.
    => 재부팅의 경우 공인 ip가 유지됩니다.


3. AWS EC2를 보면 퍼블릭 IPv4 주소는 공인 IP / 프라이빗 IPv4 주소는 사설 IP입니다.


4. VPC
    4-1. IPv4 CIDR: 10.0.0.0/16
        => VPC는 65,536개의 IPv4 주소를 포함하는 사설 네트워크 주소 공간을 갖게됩니다.
        => 실제 IP 할당은 서브넷 단위로 이루어지고, AWS가 서브넷마다 5개 주소를 예약합니다.
    
    4-2. VPC만으로 연결되지 않습니다.
        => 인터넷과 연결되는 경로가 구성되지 않았기 때문입니다.
        => 인터넷 게이트웨이, 인터넷 게이트웨이로 향하는 ROUTE TABLE 경로, 퍼블릭 ipv4를 가진 ec2, security group 필요


5. 서브넷
    5-1. VPC의 IP 주소 범위를 나누어 실제 리소스가 배치될 네트워크 구역을 정의합니다.
        => 서브넷만 생성한다고 외부에서 접속할 수 있는건 아닙니다.
    5-2. VPC라는 주소 범위 안에서 서브넷을 통해서 나눕니다.
        => 10.0.0.0/16 
        => 10.0.1.0/24, 10.0.2.0/24, 10.0.3.0/24..
        => 만약 첫 번째에 EC2를 생성한다면?
        => 자신이 속한 서브넷의 주소 범위에서 사설 IP가 할당됩니다.
        => 즉, EC2가 속한 서브넷 주소 범위에서 사설 IP가 할당됩니다.
        => 10.0.1.10, 10.0.1.23..
    5-3. 서브넷 자체가 IP 주소를 사용하는 컴퓨터가 아닙니다.
        => 10.0.1.0/24라는 서브넷을 만들었다고 해서 그 주소 범위에 컴퓨터 256대가 생기는 게 아닙니다.
        => 그 서브넷 안에 EC2를 생성하면, 
            그때 EC2에 연결된 네트워크 인터페이스가 서브넷의 IP 주소 중 하나를 할당받습니다.


6. IGW
    6-1. IGW는 VPC가 인터넷과 통신할 수 있도록 해주는 출입구입니다.
    6-2. 또한 사설 ip와 공인 ip 변환도 수행합니다.
    6-3. 외부 사용자가 EC2에 접속할 떄
        => 공인 ip를 통해서 접근 -> 인터넷 게이트웨이가 출입구 + 사설 ip로 변환 -> 해당되는 EC2에 접근
    6-4. EC2에서 외부 인터넷으로 요청할 떄
        => 목적지 ip를 보고 라우트 테이블이 어디로 전달하지 결정 -> 인터넷 게이트웨이가 출발지 ip 공인으로 변경 -> 서버 접근


7. Routing Table
    7-1. 라우팅 테이블은 패킷의 목적지 IP 주소를 보고, 그 패킷을 어디로 전달할지 결정하는 규칙입니다.
    7-2. Destination은 패킷이 도착하려는 목적지 IP주소 입니다.
    7-3. 예시
        => Destination (목적지)	Target (전달 대상)
            10.0.0.0/16	        local
            0.0.0.0/0	        igw-123456
        => 라우팅 테이블은 목적지 8.8.8.8을 확인 
        => 10.0.0.0/16에 포함되는가? → 아닙니다.
        => 0.0.0.0/0에 포함되는가? → 맞습니다.
        => 패킷을 IGW 방향으로 전달

        => 목적지가 10.0.2.10
        => 10.0.0.0/16에 포함되는가? → 맞습니다.
        => 0.0.0.0/0에도 포함되는가? → 맞습니다.
        => 더 구체적인 경로인 10.0.0.0/16 → local을 선택
        => 최장 접두사 일치(Longest Prefix Match)*라고 부릅니다.
    
    7-4. AWS에서는 각 서브넷이 반드시 하나의 라우팅 테이블과 연결되어 있습니다.
        => 서브넷마다 다른 라우팅 테이블을 사용?
        => 서브넷마다 패킷을 전달하는 경로를 다르게 설정하기 위해서 입니다.
        => A는 인터넷으로 나갈 수 있게 만들고, B는 인터넷으로 직접 나가는 경로를 만들지 않을 수 있습니다.
    
    7-5. AWS에서 서브넷에 연결하는 라우팅 테이블은 기본적으로 그 서브넷에서 다른 목적지로 전달되는 패킷의 경로를 결정합니다.
        => 그렇다고 해서 라우팅이 오직 인터넷으로 나갈 때만 사용되는 것은 아닙니다.
        => 인터넷 사용자가 EC2 웹 서버에 접속한다고 가정
            -> 요청이 들어오고 응답이 나갈 떄 라우팅 테이블을 사용합니다.
    
    7-6. 지금 구성은 외부에서 들어오는 요청은 라우트 테이블 관여 x, 응답할 떄는 라우트 테이블 관여


8. 방화벽
    8-1. 한 컴퓨터에 여러 프로그램이 동시에 네트워크 사용 가능합니다.
        => Nginx: HTTP 웹 서버, SSH 서버: 원격 접속, MySQL: 데이터베이스 서버..
        => 외부에서 패킷이 도착했을 떄 어떤 프로그램에게 전달? -> 포트 번호가 사용됩니다.
    
    8-2. IP 주소는 어느 컴퓨터로 갈지, 포트 번호는 그 컴퓨터의 어느 네트워크 서비스로 연결할지를 구분하는 데 사용합니다.
        => 범위는 0~65535, HTTP는 일반적으로 TCP 80번, HTTPS는 TCP 443번을 사용
    
    8-3. 방화벽
        => 네트워크 트래픽이 특정 조건에 맞는지 검사해서 통과시킬지 차단할지 결정하는 보안 장치 또는 소프트웨어입니다.
    
    8-4. 방화벽 가정
        => 43.202.47.71:80 → 웹 서버 / 43.202.47.71:22 → SSH 서버
        => 누구나 SSH에 서버에 접속을 시도할 수 있다면 보안 위험이 커집니다.
        => HTTP 80번: 모든 인터넷 사용자가 접속 가능, SSH 22번: 내 컴퓨터의 공인 IP에서만 접속 가능, 나머지 포트: 허용하지 않음
    
    8-5. AWS의 Security Group
        => EC2 같은 리소스의 네트워크 인터페이스에 적용하는 가상 방화벽입니다.
        => 인바운드(Inbound): 외부에서 EC2로 들어오는 트래픽 / 아웃바운드(Outbound): EC2에서 외부로 나가는 트래픽
    
    8-6. 인바운드 예시
        =>  유형	    프로토콜	포트	소스
            HTTP	    TCP	    80	    0.0.0.0/0
            SSH	        TCP	    22	    내 공인 IP/32
        => 외부 사용자가 웹 서버에 접속합니다.
        => TCP 80번 접속 요청 -> Security Group의 인바운드 규칙 확인 -> 80 / 0.0.0.0/0 -> 허용
        => 80 / 0.0.0.0/0 모든 IPv4 주소에서 TCP 80번 포트로 접근하는 트래픽 허용
        => 22 / 내 IP/32: 내 공인 IP에서 TCP 22번 포트로 접근하는 트래픽만 허용
    
    8-7. 아웃바운드 예시
        => curl https://example.com
        => EC2에서 인터넷 서버로 요청을 보내는 상황
        => TCP 443번으로 외부 요청
        => Security Group, 아웃바운드 규칙 검사
        => Security Group의 아웃바운드 규칙에서 TCP 443번 연결이 허용되어야 합니다.
        => AWS에서 새로 생성하는 보안 그룹은 일반적으로 기본 아웃바운드 규칙이 모든 트래픽을 허용하도록 되어 있지만,
             직접 제한할 수 있습니다.
    
    8-8. Security Group은 Stateful
        => 인바운드 규칙이 허용한 연결에 대한 응답은 아웃바운드 규칙과 관계없이 허용됩니다.
        => 아웃바운드 규칙이 허용한 연결에 대한 응답은 인바운드 규칙과 관계없이 허용됩니다.
    
    8-9. AWS 인바운드 규칙 구조
        => 유형 : AWS가 제공하는 규칙 프리셋 이름 (HTTP, HTTPS, SSH)
        => 프로토콜 : 네트워크에서 사용하는 통신 프로토콜 (TCP, UDP, ICMP) 
        => 포트 범위 : 해당 규칙이 허용할 목적지 포트
        => 소스 : 어떤 출발지 IP에서 들어오는 트래픽을 허용할지
        => 유형은 응용 계층이고, 프로토콜은 전송 계층
        => 프로토콜이 포트를 사용하고 신뢰성 있는 바이트 스트림을 제공합니다.

        => AWS 보안 그룹은 일반적으로 HTTP 요청의 실제 내용을 검사하지 않습니다.
        => AWS는 출발지 IP가 허용 범위에 있는가? TCP 통신인가? 목적지 포트가 80인가? 확인하고 허용합니다.


9. SSH 접속 후 curl -I https://example.com
    => DNS 조회: example.com에 대응하는 IP 주소를 알아내.
    => TCP 연결: 해당 IP의 443번 포트로 연결해.
    => TLS 연결: HTTPS 통신을 위한 암호화 연결을 설정해.
    => HTTP 요청: curl -I 옵션에 따라 HTTP HEAD 요청을 보내.
    => HTTP 응답: 실제 웹 서버가 응답을 보내.
    => example.com은 IANA가 예제와 문서 작성 용도로 관리하는 도메인입니다.
    => 즉, EC2 서버가 example.com 서버와 소통하는 것

15. ALB
    => 여러 서버로 들어오는 HTTP/HTTPS 요청을 분산하고 전달하는 서비스입니다.
    => EC2 서버가 하나뿐이라면, 해당 서버에 장애가 발생했을 때 서비스를 계속 제공하기 어렵습니다.
    => 사용자가 ALB에 요청하면 ALB가 정상 상태인 EC2 서버 중 하나를 선택해 요청을 전달
